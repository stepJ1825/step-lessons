1. Паттерн Singleton (Одиночка)
   Задача: "Глобальный логгер приложения"
Проблема: Вам необходимо создать класс ApplicationLogger для логирования событий в файл. Важно, чтобы в системе существовал только один экземпляр логгера, и чтобы он был доступен из любого места программы. Нельзя допустить ситуации, когда несколько экземпляров логгера одновременно пишут в один и тот же файл, что может привести к повреждению данных.
Требования:
Конструктор класса должен быть скрыт от внешнего использования.
Должна быть предоставлена статическая публичная точка доступа к единственному экземпляру логгера.
Реализовать метод log(String message), который добавляет переданное сообщение в файл app.log (с датой и временем).
Продемонстрировать в main, что несколько вызовов метода получения экземпляра возвращают один и тот же объект.
(Опционально, повышенная сложность) Обеспечить потокобезопасность для многопоточного приложения.
Цель: Понять важность контроля над созданием экземпляра и обеспечение глобального доступа.

2. Паттерн Factory Method (Фабричный метод)
   Задача: "Система доставки документов"
Проблема: Ваша программа работает с различными типами документов: Report, Invoice, Letter. Каждый тип документа создается немного по-разному и имеет свой собственный метод generate(). Ваш код не должен зависеть от конкретных классов документов, которые он создает.
Требования:
Создать абстрактный класс Document с методом generate().
Создать конкретные классы документов, наследующие от Document.
Создать абстрактный класс DocumentCreator с абстрактным фабричным методом createDocument(), который возвращает объект Document.
Создать конкретные создатели (например, ReportCreator, InvoiceCreator), которые реализуют фабричный метод и возвращают соответствующий конкретный объект документа.
Продемонстрировать в main, как код клиента использует DocumentCreator для работы с документами, не зная их конкретных классов.
Цель: Научиться делегировать создание объектов подклассам, делая систему расширяемой.

3. Паттерн Abstract Factory (Абстрактная фабрика)
   Задача: "Кросс-платформенный UI"
Проблема: Вы разрабатываете UI-библиотеку, которая должна поддерживать отрисовку элементов интерфейса (кнопок, чекбоксов) в двух стилях: Windows и macOS. Каждый стиль имеет свои особенности отрисовки. Нужно обеспечить, чтобы в одном приложении использовались элементы только одного стиля, и было легко добавить новый стиль (например, Linux).
Требования:
Создать интерфейсы для продуктов: Button (с методом render()) и Checkbox (с методом paint()).
Создать конкретные реализации продуктов для каждой ОС: WindowsButton, MacOSButton, WindowsCheckbox, MacOSCheckbox.
Создать интерфейс Абстрактной Фабрики GUIFactory с методами createButton() и createCheckbox().
Создать конкретные фабрики для каждой ОС: WindowsFactory и MacOSFactory, которые реализуют интерфейс GUIFactory.
Написать код клиента (Application), который принимает фабрику в качестве параметра и создает UI-элементы, используя только методы абстрактной фабрики и интерфейсы продуктов.
Продемонстрировать создание приложения в стиле Windows и macOS.
Цель: Понять, как создавать семейства взаимосвязанных объектов, не привязываясь к их конкретным классам.

4. Паттерн Builder (Строитель)
   Задача: "Создание сложного объекта 'Компьютер'"
Проблема: Класс Computer имеет много полей: cpu, ram, ssd, gpu и т.д. Некоторые поля обязательные, другие опциональные. Создавать такой объект через конструктор с 10 параметрами нечитаемо и error-prone (легко перепутать порядок аргументов). Нужно предоставить удобный способ пошагового создания объекта.
Требования:
Создать класс Computer с множеством полей (минимум 5). Сделать его конструктор приватным.
Создать статический вложенный класс ComputerBuilder. Его поля должны совпадать с полями Computer.
Реализовать в ComputerBuilder цепочковые методы (например, withCpu(String cpu), withRam(int ram)) для установки каждого параметра. Каждый метод должен возвращать this (самого себя).
Реализовать в ComputerBuilder метод build(), который проверит обязательные поля (например, cpu и ram) и, если все хорошо, вызовет приватный конструктор Computer, передав ему себя (this) в качестве аргумента.
Конструктор Computer должен принимать ComputerBuilder и копировать все значения из билдера в свои поля.
Продемонстрировать в main удобное создание разных конфигураций компьютеров.
Цель: Научиться создавать сложные объекты пошагово и избегать "телескопических конструкторов".

5. Паттерн Prototype (Прототип)
   Задача: "Система создания клонов существующих объектов"
Проблема: В вашем приложении есть сложные объекты (например, Shape с множеством полей: color, coordinates, history), создание которых с нуля через конструктор является ресурсоемкой операцией. Часто требуется создать копию существующего объекта, слегка изменив некоторые его свойства (например, позицию).
Требования:
Создать абстрактный класс Shape (или интерфейс), который реализует интерфейс Cloneable и объявляет абстрактный метод clone().
Создать конкретные классы-наследники, например, Circle и Rectangle, с несколькими полями.
Реализовать метод clone() в каждом конкретном классе. Внутри метода нужно создать копию объекта, корректно скопировав все его поля (рекомендуется использовать глубокое копирование, особенно для mutable-полей, например, массивов или коллекций).
Продемонстрировать в main создание прототипа, а затем быстрое создание его клонов с модификацией отдельных свойств.
Цель: Понять, как клонирование существующих объектов может быть эффективнее создания новых.

6. Комбинированная задача на выбор паттерна
   Задача: "Конфигурация подключения к базе данных"
Проблема: Вам нужно спроектировать систему для работы с подключениями к различным СУБД (MySQL, PostgreSQL). Подключение к БД — дорогостоящий ресурс, и в рамках одного приложения должно существовать только одно подключение к конкретной БД. Конфигурация для подключения (URL, логин, пароль) должна считываться из файла и быть единой для всех.
Постановка вопроса:
Какой порождающий паттерн вы выберете для управления единственным экземпляром подключения? Обоснуйте.
Какой паттерн поможет создать объект подключения в зависимости от типа БД (MySQL или Postgres), если они имеют общий интерфейс Connection? Обоснуйте.
Реализуйте систему, используя выбранные вами паттерны.
Ожидаемый ответ и реализация:
Для управления единственным экземпляром — Singleton. Он гарантирует единственность точки доступа.
Для создания подключения в зависимости от типа — Factory Method или Abstract Factory. Здесь достаточно Factory Method, так у нас есть только один продукт — Connection.
Реализация: Класс DatabaseConnection (Singleton) внутри себя использует ConnectionFactory (с фабричным методом createConnection()), чтобы создать конкретное подключение (MySQLConnection или PostgresConnection). Конфигурация для фабрики и тип БД считываются Singleton'ом из файла при его инициализации.
